# Vesutil — модель аккаунтов и доступа компаний (черновик 0.1)

## Цель
Подготовить многопользовательский кабинет компаний до подключения реальной регистрации и PostgreSQL. Одна компания может иметь несколько филиалов, предложений и сотрудников.

## Сущности
- `app_users`: профиль пользователя, связанный с внешним провайдером авторизации по паре `auth_provider + auth_subject`. Пароли в базе Vesutil не хранятся.
- `company_memberships`: связь пользователя с компанией и его роль.
- `company_invitations`: приглашение сотрудника по email. В БД хранится только хеш одноразового токена.
- `audit_events`: история важных действий с компанией, филиалами, предложениями и ценами.

## Роли первой версии
| Роль | Права |
|---|---|
| owner | Полное управление компанией, сотрудниками и назначение нового владельца по отдельному защищённому сценарию |
| admin | Профиль, филиалы, предложения, прайсы и приглашения сотрудников; без передачи владения |
| editor | Создание и изменение филиалов/предложений/прайсов; без управления сотрудниками |
| viewer | Только просмотр кабинета и данных компании |

Роль применяется на уровне компании. В первой версии не вводим индивидуальные права на каждый филиал — это усложнит интерфейс без подтверждённой потребности.

## Основные правила безопасности
1. Пользователь может читать или изменять компанию только при активном членстве в ней.
2. Нельзя доверять `company_id`, `branch_id`, роли или user ID, пришедшим из браузера: сервер получает пользователя из проверенной сессии и сам проверяет членство.
3. Все операции с филиалом/предложением сначала проверяют принадлежность ресурса компании.
4. Только owner/admin управляют приглашениями; только owner передаёт владение.
5. Токены приглашений генерируются криптографически стойкими, в БД хранится только хеш; токен одноразовый и ограничен по времени.
6. Смена цены, статуса предложения, реквизитов и состава участников записывается в аудит.
7. Сотрудник, покинувший компанию или заблокированный, сразу теряет доступ.
8. Публичный каталог отдаёт только опубликованные предложения и только публичные поля. Контакты и закрытые данные не должны случайно попадать в публичный API.

## Регистрация и создание компании
1. Пользователь проходит регистрацию у выбранного провайдера авторизации.
2. Сервер проверяет сессию и создаёт/обновляет запись `app_users`.
3. Пользователь создаёт компанию; в одной транзакции создаются `companies` и членство с ролью `owner`.
4. Создатель добавляет филиалы и предложения. До публикации они имеют статус draft.
5. Приглашённый сотрудник принимает приглашение; сервер проверяет хеш токена, срок, email и статус, затем создаёт членство и закрывает приглашение.

## Что пока не выбрано
- Провайдер авторизации (например, Supabase Auth или отдельный OIDC-провайдер).
- Почтовый провайдер для приглашений и подтверждения email.
- Правила проверки ИНН/ОГРН и подтверждения владения компанией.
- Политика хранения персональных данных, согласия и сроки удаления.
- Точный перечень публичных/закрытых полей карточки филиала.

## Границы текущей реализации
Миграция `0002_company_access.sql` создаёт таблицы и индексы, но не включает подключение БД, регистрацию, сессии, RLS или production-политики. До выбора провайдера и проверки серверной модели доступа нельзя открывать прямой доступ к БД из браузера. Секреты и ключи хранятся только в серверных переменных окружения.

## Следующий технический шаг
Выбрать провайдера авторизации и схему подключения PostgreSQL. После этого реализовать серверные проверки ролей и тесты изоляции компаний, затем включить регистрацию и сохранение кабинета.
